# `day4/simple_agent.ipynb` vs `day2/security_rag_advance` 비교

두 실습 모두 **"보안 취약점에 대해 LLM에게 어떻게 대응책을 물을 것인가"**를 다룬다.
하지만 접근 방식이 정반대에 가깝고, `simple_agent.ipynb`가 보여주는 실패가
`security_rag_advance`가 존재하는 이유이기도 하다.

## 한 줄 요약

| | `simple_agent.ipynb` | `security_rag_advance` |
|---|---|---|
| 접근 | LLM 체인 (LLM → LLM → LLM) | RAG (검색 + 계산 + LLM) |
| 근거 | **모델의 기억(parametric memory)뿐** | NVD·OSV·Red Hat·CISA KEV 등 실제 문서·API |
| CVE/CWE ID를 얻는 방법 | LLM에게 "맞혀보라"고 질문 | 벡터 검색 + 메타데이터 필터로 조회 |
| 버전 영향 판정 | 하지 않음 (애초에 불가능) | `check_version()`으로 부등호 계산 |
| 결과의 신뢰성 | **틀려도 그럴듯하게 말함** (검증된 실패 사례 포함) | 틀린 근거를 넣을 수 없는 구조 (근거가 없으면 "모른다"고 명시) |
| 노트북의 목적 | 체인 구조 자체를 가르치고, **왜 이 방식이 위험한지** 보여줌 | 실무에서 쓸 수 있는 수준의 CVE 대응 어시스턴트 구현 |

## 1. 구조 비교

### `simple_agent.ipynb` — 역할 분리형 LLM 체인

```
[1단계] 취약점 설명 → CVE ID 찾기   OpenAI gpt-4.1-mini
            ↓ cve_id (f-string으로 다음 단계에 삽입)
[2단계] 취약점 설명 → CWE ID 찾기   Google gemini
            ↓ cwe_id
[3단계] CVE + CWE → 대응 방안 작성   OpenAI o3
```

- 세 모델 모두 **OpenAI 호환 엔드포인트**로 통일해서 `base_url`만 바꿔 호출한다 (`openai`, `gemini`, `anthropic` 세 클라이언트가 모두 `OpenAI()` 클래스).
- 체인의 연결 고리는 f-string 변수 삽입이 전부다. 별도 프레임워크나 검증 로직이 없다.
- **검색이 전혀 없다.** 세 단계 모두 LLM이 사전 학습 때 외운 지식만으로 답한다.

### `security_rag_advance` — 검색 + 계산 + 생성 파이프라인

```
[0] 수집            NVD / CISA KEV / FIRST EPSS / OSV / Red Hat / MITRE CWE
        ↓
[1] 청킹            소스 유형별로 다른 분할 전략 (섹션 단위 / 문단 단위 / 필드 단위)
        ↓
[2] 임베딩·저장      Chroma 벡터 DB (scope=type ↔ CWE, scope=instance ↔ 어드바이저리)
        ↓
[3] 질의            위험도·버전 판정은 "계산", 설명·대응은 "검색" — 구획을 나눠 프롬프트에 주입
```

- CVE/CWE 번호를 LLM이 **추측하지 않는다.** 메타데이터 필터와 정규식 추출(`extract_cve_id`)로 정확히 뽑는다.
- 버전이 영향을 받는지는 LLM에게 묻지 않고 `check_version()`이 OSV의 `introduced <= version < fixed`를 실제 비교 연산으로 판정한다.
- CVSS·EPSS·KEV 같은 숫자는 벡터 검색이 아니라 `cve_core.json`에서 그대로 읽어 그대로 넣는다.
- CWE 설명·완화책·대응 방안은 벡터 검색 근거를 프롬프트에 구획(`<위험도>`, `<버전 판정>`, `<어드바이저리>`, `<취약점 유형>`)으로 나눠 넣는다.

## 2. 핵심 차이: "안다"와 "찍는다"의 구분

`simple_agent.ipynb`의 Step 6(`logprobs` 실험)이 이 비교의 핵심을 가장 잘 보여준다.

- `CVE-` 라는 **형식**은 모델이 100% 확신한다.
- 하지만 뒤에 오는 **숫자**는 확신도가 67~96%로 떨어진다. 즉, 모델은 "CVE ID처럼 생긴 문자열을 만드는 법"은 알지만 "그 사건의 진짜 번호"는 모른다.
- 실제로 노트북에 저장된 실행 결과를 보면, 같은 질문(Google Chromium V8 타입 혼동 취약점)에 대해 실행할 때마다 `CVE-2023-2033`, `CVE-2022-0609`, `CVE-2023-2146` 등 **서로 다른 CVE ID**가 나왔고, 최종 3단계 답변은 원래 질문과 무관한 **OpenSSL** 취약점 이야기를 그럴듯하게 생성했다.
- `temperature=0`으로도 완전히 해결되지 않는다 — 노트북이 명시하듯 "일관성을 높일 뿐 정확성을 주지 않는다." 틀린 답을 일관되게 내놓을 수도 있다.

`security_rag_advance`는 이 문제를 **구조적으로 차단**한다.

- ID 자체를 LLM에게 묻지 않는다 (정규식 추출 또는 사용자가 직접 CVE ID를 입력).
- CWE 설명도 "LLM의 기억"이 아니라 **색인된 MITRE 원문 청크**에서 가져온다.
- 수집되지 않은 CVE를 만나면 NVD/KEV/EPSS를 실시간 조회해서라도 사실을 확보하고, 그래도 어드바이저리가 없으면 "패치 버전·조치 기한은 답할 수 없다"고 **명시적으로 모른다고 말한다** — `simple_agent.ipynb`의 3단계처럼 근거 없이 구체적인 숫자(영향 버전, CVSS 점수)를 지어내지 않는다.
- "확인하지 못함"과 "없음"을 구분한다 (KEV 조회 실패 ≠ KEV 미등재). 이는 `simple_agent.ipynb`에는 아예 없는 개념이다 — 그쪽은 모델이 모르는 상태 자체를 감지하지 못한다.

## 3. 오류 전파 방식의 차이

`simple_agent.ipynb`는 **체인이 길어질수록 오류가 증폭**되는 구조다.

- 1단계가 틀린 CVE ID를 내놓으면, 2·3단계는 그것을 사실로 받아들이고 이야기를 이어간다.
- 중간에 검증 단계가 없다 (노트북 스스로 "스스로 해보기" 과제로 "ID 형식 검사 코드를 넣어보라"고 제안하지만 구현되어 있지는 않다).
- 3단계는 틀렸다는 신호를 전혀 주지 않고 그럴듯한 형식(영향 버전, CVSS 점수, 대응 절차)으로 답을 완성한다 — 노트북이 "이것이 가장 위험한 부분"이라고 명시.

`security_rag_advance`는 **각 단계의 산출물이 서로 다른 신뢰 등급으로 분리**되어 있어 오류가 섞이지 않는다.

- 위험도·버전 판정 = "계산된 사실" (재계산 금지 지시와 함께 프롬프트에 주입)
- CWE/어드바이저리 설명 = "검색된 근거" (출처가 명확한 청크)
- 이 둘을 프롬프트에서 구획을 나눠 LLM에게 "사실은 그대로 전달하고, 설명은 근거 안에서만 하라"고 지시한다.
- `common.check_backend_match()`, `len(chunks.json) == collection.count()` 같은 정합성 체크를 통해 색인 상태 자체의 오류도 조기에 잡는다.

## 4. 공통점

- 둘 다 **역할을 세분화**한다는 설계 철학은 같다 — `simple_agent.ipynb`는 모델별로, `security_rag_advance`는 데이터 소스·처리 단계별로 역할을 나눈다.
- 둘 다 **중간 산출물을 다음 단계의 입력으로 넘기는 체인/파이프라인** 구조다.
- 둘 다 CVE → CWE → 대응방안이라는 동일한 질문 구조를 다룬다.
- 둘 다 출력 형식을 좁게 지정하는 것의 중요성을 강조한다(`simple_agent`의 "ID만 답하라" 지시 vs `security_rag_advance`의 메타데이터 필터·스키마 고정).

## 5. 결론 — 이 둘은 같은 문제의 "전(前)"과 "후(後)"

`simple_agent.ipynb`는 노트북 스스로 마지막 정리에서 밝히듯, **여러 LLM을 체인으로 잇는 방법을 가르치는 동시에 "왜 RAG가 필요한지"를 보여주기 위해 의도적으로 실패하도록 설계**되어 있다. 노트북 말미의 "어떻게 고치나" 표가 가리키는 세 방향 중 첫 번째("실제 데이터를 검색해서 넣기")가 바로 `security_rag_advance`가 구현한 것이다.

즉,

- `simple_agent.ipynb` = **체인(chain) 패턴의 입문** + **parametric memory만으로는 사실을 담보할 수 없다는 반면교사**
- `security_rag_advance` = 그 문제(모르면서 찍는 LLM, 오류 전파, 근거 없는 확신)를 **검색 근거 + 구조화 계산 + 신뢰도 구분**으로 해결한 실무형 구현체

둘을 이어서 보면 "왜 단순 체인이 위험한가 → RAG와 계산 분리가 이를 어떻게 막는가"라는 하나의 학습 흐름이 완성된다.
